# AI 工程师调用与项目推进流程

## 1. 指挥关系

本项目采用四级控制：

```text
项目指挥者（用户）：决定何时调用哪位工程师、批准阶段推进
        ↓
总负责人（当前助手）：拆解任务、检查前置条件、独立验收、总结进度
        ↓
AI 数据工程师 / AI 算法工程师 / AI 应用工程师：一次只执行一个阶段
        ↓
Git、测试和 artifacts：保存可复核证据
```

工程师不能自行跨阶段。每个阶段必须经历“派工 -> 实施 -> 阶段报告 -> 总负责人验收 -> 用户批准”五步。未通过的任务退回原工程师修复，不允许下游绕过问题。

## 2. 当前基线

截至 2026-08-09，目录、203 类 taxonomy、数据完整性审计、工程骨架和 CUDA 环境已就绪。当前不是“数据工程完成”状态：manifest、坏图清单、重复组和固定 split 尚未生成。正式开发从 `D0` 开始。

动态验收状态只记录在 `docs/acceptance-checklist.md`。三位工程师的实施过程分别记录在 `docs/worklogs/`，总负责人的复验与决策记录在 `docs/worklogs/project-lead.md`。计划文档描述规则，不用“计划完成”代替实际验收。

## 4. 用户派工模板

每次只调用一个工程师执行一个阶段。可直接使用：

```text
请调用 AI <数据/算法/应用>工程师执行 <阶段 ID>。
只完成该阶段，不得进入下一阶段。
前置版本或 Git commit：<由总负责人填写>。
允许修改范围：<由职责文档填写>。
必须交付：<该阶段交付物>。
完成后运行规定测试，并按阶段完成报告模板汇报；不要自行提交或推送，除非我明确要求。
```

推荐调用顺序：先让总负责人确认阶段前置条件，再由用户发出派工指令。工程师不能以“顺手优化”为由修改其他角色负责的文件。

首次调用或更换会话时，先发送 `docs/prompts/` 中对应角色的启动提示词。工程师返回预备状态后，再发送本节的阶段派工指令。启动提示词本身不授权修改文件。

## 5. 阶段完成报告模板

```markdown
# <阶段 ID> 完成报告

- 状态：待验收 / 阻塞
- 输入版本：数据、模型、taxonomy、Git commit
- 修改文件：逐项列出
- 生成产物：路径、版本、SHA-256
- 执行命令：命令、退出码、关键输出
- 验收矩阵：每项标准对应证据
- 关键统计：样本、指标、耗时、显存等适用数据
- 偏差与风险：与计划不同之处、遗留问题
- Git 状态：已跟踪和未跟踪改动
- 边界声明：未执行下一阶段
```

“代码已完成”或“运行正常”不构成交付。报告必须包含可由总负责人重新执行的命令和机器可核验结果。

## 6. 总负责人验收流程

总负责人在工程师交付后执行以下动作：

1. 检查修改是否超出允许目录，识别用户原有改动并避免覆盖。
2. 对照 `acceptance-checklist.md` 检查文件、版本、校验和和统计。
3. 独立重跑测试、审计或最小推理，不只引用工程师报告。
4. 检查数据泄漏、测试集调参、标签漂移、预处理不一致等高风险问题。
5. 给出唯一结论：`通过`、`退回` 或 `阻塞`，并记录证据。
6. 汇总当前完成度、风险、下一阶段建议，由用户决定是否继续调用。

`退回` 表示同一阶段有可修复问题；`阻塞` 表示缺少输入、权限、硬件或用户决策。只有 `通过` 才能满足下游前置条件。

## 7. 版本和变更控制

- taxonomy、split、模型包和应用发布包均使用不可覆盖的版本目录。
- 原始图像禁止删除、移动、重命名或原地修改。
- 类别 ID、宿主或四大类语义需要变更时，工程师只提交变更申请，由用户和总负责人批准后生成新版本。
- 训练实验不得覆盖旧 run；测试集只在模型方案冻结后评估一次。
- 工程师默认不提交、不推送。Git 提交边界和提交信息由总负责人检查后，用户明确下令执行。
- `artifacts/` 是可再生本地证据目录，不纳入 Git；正式报告应保留关键统计、配置和校验和。
- 每位工程师只能追加自己的 `docs/worklogs/` 日志；总负责人是 `project-lead.md` 和验收状态的唯一维护者。
- 日志保存摘要和证据索引，不粘贴大段控制台输出，不提交模型、完整 CSV 或图片。

## 8. 每次验收后的汇总格式

总负责人向用户报告：阶段结论、关键证据、发现的问题、当前整体状态、下一位建议调用的工程师及阶段 ID。未通过时只建议返工当前阶段，不提前派发下游任务。
